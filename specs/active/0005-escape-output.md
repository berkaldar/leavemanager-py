# Spec 0005 — Escape all page output (stored XSS, B-8)

- Status: In progress
- Mode: lite
- Plan: `specs/plans/0005-plan.md`
- Self-critique: done

## Intent
Anyone who can file a request can type markup or a script into the reason field, and every
colleague who opens the request list then runs it. Employee names and departments are shown the
same way. Success means that every piece of stored text appears on the page exactly as it was
typed — as plain text, never as markup — on all three pages. Nothing else about the pages
changes, and nothing stored needs cleaning up, because the data lives in memory.

## Requirements
- R-1 Stored text (names, departments, reasons, status values) is shown as text wherever a page
  shows it.
- R-2 All five HTML-special characters are covered: `<`, `>`, `&`, `"`, `'`.
- R-3 Text is escaped once: what a user typed is what a user sees, even when it already looks like
  an HTML entity.
- R-4 For ordinary data (no special characters) every page is exactly as before.
- R-5 The shipped tests that pin the unescaped behavior are changed on purpose, in this spec, and
  nowhere else: `test_markup_is_not_escaped` (4 cases) in `tests/test_pages.py` and
  `test_markup_in_reason_is_not_escaped` and
  `test_markup_in_employee_name_is_not_escaped_in_dropdown` in `tests/test_new_request.py`.
- R-6 The same holds for the signed-in username in the navigation.

## User experience
- Flow: unchanged. A user reads the dashboard, the request list and the new-request page; text
  that contains markup is displayed literally.
- States: populated pages with text that contains markup (new here); every other state is as
  pinned by specs 0002–0004. There is no loading, error or no-permission state of its own.
- Design reference: none — the current pages are the design; only how stored text is rendered
  changes.
- Accessibility: none today; not changed by this spec.
- Screenshots for SHIP (docs/testing.md, Evidence for UI criteria): the dashboard, the request
  list and the new-request dropdown, each showing markup-laden data as literal text — captured by
  VERIFY, headless, outside the repo, deleted after the SHIP gate.

## Constraints & out of scope
- Sensitive area: Employee personal data; Leave balance calculation (the pages show every
  employee's balance); Authentication (a script on a page runs with the signed-in user's rights).
- No new dependency: escaping comes from Flask and Jinja, already installed.
- Resolves backlog item B-8; its entry is deleted in the ship commit. The missing Content-Security-
  Policy and other security headers are recorded as B-12 and are not part of this spec.
- Supersedes: 0002/AC-6 and 0003/AC-9 (both pin the unescaped output; they now pin the escaped
  output with the same inputs and the same pages). Their `OPEN B-8` markers are removed in the
  same change. The other shipped criteria keep their values.
- Every other string on the pages is fixed text or generated by the application (messages,
  labels, the hex CSRF token, dates that come from parsed dates), so nothing else is escaped or
  changes.
- Out of scope: limiting the reason's length or validating input (B-10); debug mode (B-9); what
  each role may see (roles spec); a Content-Security-Policy (B-12); cleaning stored data (none is
  stored beyond a process).

## Acceptance criteria
"Today" is 2026-11-21 and the data is the seed data unless a criterion says otherwise. The user is
signed in (as in specs 0002–0004). "The page shows X as text" means: parsed the way a browser parses
it, X is text content and creates no element; in the page source `<` appears as `&lt;`.
- [ ] AC-1 — Dashboard: an employee name or department containing `<b>x</b>` is shown as the text
  `<b>x</b>` (source: `&lt;b&gt;x&lt;/b&gt;`), not as bold text.
- [ ] AC-2 — Request list: an employee name, and a reason submitted through the new-request form,
  containing `<b>x</b>` are shown as the text `<b>x</b>`; so is a status value containing it (no
  page can set a status, so the test stores one directly; the label keeps its gray fallback
  color).
- [ ] AC-3 — New-request page: an employee name containing `<b>x</b>` is shown as the text
  `<b>x</b>` in the dropdown option, and the dropdown still lists exactly five options.
- [ ] AC-4 — All five special characters: a text `<>&"'` is shown as exactly those five
  characters — in a name on the dashboard, on the request list and in the dropdown; in a
  department on the dashboard; in a reason on the request list — and creates no element and no
  attribute (judged by parsing the page the way a browser does).
- [ ] AC-5 — A text `<script>alert(1)</script>` in a name, a department or a reason is shown as
  text on every page that shows it (same places as AC-4); no page then contains a `script`
  element made from it.
- [ ] AC-6 — Escaped once: a text typed as `Tom &amp; Jerry` is shown as `Tom &amp; Jerry` (not
  as `Tom & Jerry`), in the source as `Tom &amp;amp; Jerry`.
- [ ] AC-7 — Ordinary data is unchanged: with data that has no special characters, every page is
  exactly as before this spec. The existing 91 tests pass with the same values and assertions;
  the only edits to them are the flipped tests named in R-5 and Supersedes.
- [ ] AC-8 — Navigation: a signed-in username containing `<b>x</b>` is shown as the text
  `<b>x</b>` next to the "Cikis" button, on every page.
